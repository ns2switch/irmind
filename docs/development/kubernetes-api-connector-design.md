# Read-only Kubernetes API connector

This proposal covers current-state collection from an explicitly configured
Kubernetes API server. It does not implement a connector. Offline audit logs and
Falco alerts remain separate parser and mapping modules; a state snapshot cannot
replace historical audit evidence.

## Purpose and boundaries

An analyst investigating audit events may need to check the current RBAC graph,
pods and service accounts. A future optional connector would expose bounded
structured reads. It would never execute commands, attach to a pod, port-forward,
read container logs, retrieve Secrets, issue TokenRequests, modify RBAC, or create
any cluster resource. No arbitrary API path, JSONPath expression, shell command
or free-form query supplied by the model would be accepted.

The organization policy and case must both name the cluster and permitted
namespaces. A server URL is transport configuration, not proof that two clusters
share an identity. The explicit stable cluster identity used by offline records
also scopes connector entities; identical pod or account names in other clusters
must remain distinct.

## Configuration and credentials

`/settings connectors` would contain the HTTPS server URL, source ID, stable
cluster identity, allowed namespaces, request limits and optional connector CA
PEM. The existing per-connector CA mechanism retains system roots, hostname
verification and a signed PEM fingerprint. Redirects to another origin are
rejected. There is no insecure TLS setting.

A ServiceAccount bearer token is an explicit credential stored in SecretBackend.
It is never accepted in command arguments, environment variables, config.toml,
case text or exported request headers. Expiry or revocation is a visible error
with instructions to replace the credential in settings; no automatic privilege
change occurs. Loading kubeconfig, ambient cloud credentials, in-cluster tokens,
credential helper executables or exec authentication plugins is excluded.

Adding this credential and any future client certificate option requires a
separate reviewed contract before implementation. Token generation and initial
RBAC binding are administrator actions outside IRMind.

## Proposed port and structured operations

A new local application port would accept a validated request containing:

- Source ID and stable cluster identity.
- A closed resource enum: Pod, ServiceAccount, Role, RoleBinding; optional
  ClusterRole and ClusterRoleBinding reads require explicit cluster-wide scope.
- A namespace for namespaced resources, optional exact object name and bounded
  literal label matches. Resource names and namespaces use Kubernetes identifier
  validation; selectors are generated by the connector with escaped values.
- A result count and cancellation token, intersected with case and policy limits.

The connector translates this request to allowlisted `get` or `list` endpoints
for core/v1 and rbac.authorization.k8s.io/v1. It never accepts a model-authored
URL, method, API version, field projection or impersonation header. Namespace
lists are explicit; an empty list means no access, not every namespace.

The port would return bounded original JSON plus acquisition metadata, response
resourceVersion, truncation status and decoder identity. It must feed the same
SourceRecord and identified mapping stages as offline modules. It is not an
extension of the parser's capabilities. Approving this design would not approve
the port or new case-scope fields; their exact signatures and canonical bytes
need review before code is added.

## Minimum permissions

For each permitted namespace, a Role needs only `get` and `list` on `pods` and
`serviceaccounts` in the core API group, and on `roles` and `rolebindings` in
`rbac.authorization.k8s.io`. Bind it to the dedicated ServiceAccount using a
RoleBinding in that namespace. It needs no `watch`, create, update, patch, delete,
impersonate, bind or escalate permission and no access to subresources.

The built-in `view` role is not the permission specification: its contents can be
aggregated or changed by cluster administrators. Use an explicit reviewed Role.
If cluster-level RBAC inspection is enabled, a separate narrowly scoped
ClusterRole grants only `get` and `list` on `clusterroles` and
`clusterrolebindings`. This is broader visibility and requires explicit analyst
confirmation, an organization ceiling and a signed effective-scope record. A
namespace-only case cannot request these objects, even if its token can read
them. Permission failures never trigger fallback to broader credentials.

## Bounds, cancellation and evidence

Initial proposed ceilings are 100 objects per page, 1,000 objects per operation,
1 MiB per object, 8 MiB decompressed per response, 32 MiB per operation and a
10-second wall-clock deadline. Final values must be checked against synthetic
large Pod and RBAC responses before approval. Enforce response and decompression
bounds before parsing, as well as depth, field count and string limits. Check
cancellation between chunks and pages; a slow peer cannot hold the case lock
indefinitely.

Pagination preserves the server's resourceVersion and treats its continuation
token as opaque untrusted data with a length bound. Expired tokens, inconsistent
versions and API errors produce an explicit incomplete result, never a claim of
a complete snapshot. Do not silently restart a list at a newer state. No watch
stream is included.

Original responses are signed evidence with server identity, validated selector,
API/resource version, acquisition time and a bounded summary. Authentication
headers, tokens and secret-valued annotations are never echoed in diagnostics.
Collection must document that requested objects can still contain sensitive
metadata. `creationTimestamp` is object metadata, not the time at which a queried
state or historical action occurred. A current-state observation is labeled as
such; it cannot establish that an old permission assignment existed during an
incident.

All returned fields remain tainted with cluster, source, object and record
provenance. The guard screens model and display projections. Resource content
cannot choose tools or change scope, credential selection, limits or policy.
Calls consume case budgets, and outbound reads use the existing approval rules.
The model never changes the configured namespace or cluster-wide mode.

## TUI and contracts

The analyst configures transport and a keystore credential in settings, reviews
effective cluster/namespace scope and explicitly enables the source. Case cards
show current-state observations and truncation, with exact structured request
arguments available in details. Missing permission, expired token, TLS failure,
rate limiting and cancellation each leave a visible result. The case continues
to work with offline evidence when the connector is unavailable.

The shared connector suite should cover correct get/list translation, strict
namespace and organization ceilings, no subresources or write verbs, hostile
names and selectors, token redaction, private-CA success and hostname mismatch,
bounded bodies and pagination, cancellation, resourceVersion expiry and signed
export verification. A malicious synthetic API response plus the obedient model
must fail to induce Secret reads, exec, impersonation or out-of-scope requests.

## Dependencies and implementation gate

The first implementation can reuse the workspace HTTP/TLS client, JSON decoder,
URL validation, SecretBackend and CA verification. No Kubernetes SDK is required
for this small fixed API surface. Any `kube`, `k8s-openapi`, JWT or authentication
helper dependency would need a separate justification and approval. No new
production dependency or credential is introduced by this document.
